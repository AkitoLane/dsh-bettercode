# Code Smells 目录：症状、病因、处方

重构前的诊断手册。每条：怎么认出来（症状）→ 为什么出现（病因）→ 怎么改（处方）。
红线清单见 SKILL.md「反屎山红线」；本表供逐条排查。

## 结构类

### Long Function（过长函数）
- 症状：> 40 行；需要用"然后…然后…"复述逻辑；靠注释分段。
- 病因：职责不断追加，没人愿意拆。
- 处方：Extract Method。每段注释就是一个新函数的名字；按抽象层级拆分。

### God Object（上帝对象/模块）
- 症状：一个类/文件管配置、管 I/O、管业务、管缓存；改什么都碰它。
- 病因：图方便，塞进最顺手的地方。
- 处方：按"每次变更的理由"划分边界（SRP），拆成多个协作模块。

### Deep Nesting（嵌套过深）
- 症状：缩进 ≥ 4 层；if 套 if 套 for 套 try。
- 病因：没有用 guard clause 处理例外。
- 处方：早返回处理边界与错误；循环体提取成函数；条件取反后 continue/return。

### Long Parameter List（参数过长）
- 症状：> 4 个参数；调用处全是 `true, false, null`。
- 病因：函数想做的事太多，或缺一个值对象。
- 处方：Parameter Object（聚合成结构体/options 对象）；删掉可推导的参数；拆函数。

### Mixed Abstraction Levels（抽象层级混杂）
- 症状：一个函数里既有"处理订单"这样的策略语句，又有位运算/字符串切片这样的细节。
- 病因：细节没有下沉。
- 处方：低层细节 Extract Method，让主函数只剩一层策略语句，读起来像清单。

## 重复与死物

### Duplicated Code（重复代码）
- 症状：两段代码形状相同只差标识符；改一处必须记得改另一处。
- 病因：复制粘贴最快。
- 处方：第 3 次出现必须抽象（Rule of Three）；提函数/提模块/模板化；重复的是"结构"而非字面时，先找共同抽象再动手。

### Dead Code（死代码）
- 症状：注释掉的代码块；永假的分支；没人调用的导出；被绕过的旧实现。
- 病因：不敢删。
- 处方：删。版本控制记得一切。不确定就用"删除 + 可从历史找回"代替"注释保留"。

### Speculative Generality（过早通用化）
- 症状：只有一个实现的接口；永远为空的 hook 参数；"以后可能会用"的配置项。
- 病因：为想象中的需求设计。
- 处方：删到只剩当前需要的形状；需求真来了（第三次重复时）再泛化。

## 命名与表达

### Mysterious Name（含糊命名）
- 症状：`data`、`info`、`temp`、`flag`、`obj`、`doSomething`、`handle`、`process`、裸 `util` / `manager`。
- 病因：起名时还没想清楚它是什么。
- 处方：领域词 + 角色重命名（`retryCount`、`isEligible`、`parseConfig`）；函数名 = 动词 + 宾语；布尔 = is/has/can/should。

### Boolean Trap（布尔陷阱 / Flag Argument）
- 症状：`f(true, false)`；函数体内 `if (flag)` 分叉出两套逻辑。
- 病因：用参数省了一次拆分。
- 处方：拆成两个语义函数；或传枚举/options 对象；调用处永远可读。

### Magic Number/String（魔法值）
- 症状：`if (status == 3)`、`retry(5)`、裸 URL 散落各处。
- 病因：写的时候图快。
- 处方：具名常量集中定义；状态用枚举；常量名本身就是文档。

### Comment Smell（注释异味）
- 症状：注释复述代码（`// 循环用户列表`）；注释掉的旧代码；注释与代码矛盾。
- 病因：代码表达力不足的补偿。
- 处方：Extract Method + 好命名让"是什么"注释多余；注释只保留"为什么"（约束、坑、取舍、测量数据）；过期注释是 bug，删或改。

## 边界与耦合

### Shotgun Surgery（霰弹式修改）
- 症状：加一个字段/改一个规则要动 3+ 个文件。
- 病因：一个职责被打散到多处。
- 处方：Move Method/Field 把同一变更理由的代码聚拢；引入中间层隔离变化点。

### Feature Envy（依恋情结）
- 症状：函数 A 里全是访问对象 B 的数据；`a.getB().getC().getD()` 链式穿透。
- 病因：行为放错了家。
- 处方：把函数移到它最依恋的数据旁边；用 Law of Demeter 收拢链式访问（只和直接朋友说话）。

### Inappropriate Intimacy（不当亲密）
- 症状：两个模块互访对方私有细节、互相 import、职责分不清。
- 病因：边界没设计。
- 处方：Move Method 划清各自职责；用接口/事件解耦；亲密关系要么合并要么解耦，不要暧昧。

### Temporal Coupling（时序耦合）
- 症状：必须先调 `init()` 再调 `run()` 否则崩；顺序知识只存在于文档/口头。
- 病因：生命周期没有封装。
- 处方：合并成一个入口函数在内部管理顺序；或用 builder/类型系统强制顺序。

### Primitive Obsession（基本类型偏执）
- 症状：用 string 表示枚举、int 表示金额/ID、map 传来传去当对象。
- 病因：不想建类型。
- 处方：建值对象/枚举/别名类型；校验放进类型构造函数，一次校验处处安全。

## 错误与状态

### Swallowed Error（被吞的错误）
- 症状：空 catch；`except: pass`；catch 后返回伪装成功的默认值。
- 病因：让报错消失最快。
- 处方：每个 catch 三选一，恢复、加上下文重抛、记录后终止。错误信息带定位上下文（操作 + 输入）。

### Exception as Control Flow（异常当控制流）
- 症状：用 try/catch 做正常分支；可预期的失败走异常通道。
- 病因：没设计错误通道。
- 处方：可预期失败用 Result/Option/错误码返回；异常只留给真正的异常。

### Mutable Global State（可变全局状态）
- 症状：模块级可变变量；单例里存业务状态；测试互相污染、顺序敏感。
- 病因：传参麻烦。
- 处方：依赖注入代替全局读取；状态收进明确的 owner；能不可变就不可变。

### Hidden Side Effect（隐藏副作用）
- 症状：函数名说"查询"，实际还写缓存/发请求/改入参。
- 病因：顺手。
- 处方：命令查询分离（CQS）；查询无副作用；副作用函数名字带动词（`fetchAndCache`）；不修改入参，返回新值。

## 重构操作守则

1. **小步前进**：一次一个处方，改完立即验证（跑测试/运行一次），再改下一个。
2. **测试先行**：没有测试的代码，先补一组特征测试（characterization tests）锁住当前行为，再动刀。
3. **不改行为**：重构 = 改结构不改行为；要改行为另起一次提交。
4. **童子军军规**：离开时比来时干净一点，但"一点"必须小步、可验证。
