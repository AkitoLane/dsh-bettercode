# Performance Patterns 速查

语言无关的性能模式，是 SKILL.md Phase 4 的展开参考。
原则不变：**宏观靠设计，微观靠测量。**

## 1. 数据结构选择表

先写"我需要什么操作 + 目标复杂度"，再从表里选结构。

| 需求 | 选择 | 关键复杂度 |
|---|---|---|
| 按 key 查找 / 去重 | Hash Map / Set | 查插删 O(1) 均摊 |
| 成员判断（循环里高频） | Set，绝不遍历 List | O(1) vs O(n) |
| 有序 + 动态插入 | 平衡树 / SkipList / sorted 容器 | O(log n) |
| 有序 + 只读 | 排序数组 + 二分 | 查 O(log n)，内存最省、缓存最友好 |
| Top-K / 优先级调度 | 堆（Heap / PriorityQueue） | 插入与取顶 O(log n) |
| FIFO / LIFO | Deque / Queue / Stack | 两端 O(1) |
| 区间查询（和 / 最值） | 前缀和（静态）/ 线段树或树状数组（动态） | O(1) ~ O(log n) |
| 图 | 邻接表（稀疏）/ 邻接矩阵（稠密且小） | 遍历 O(V+E) |
| 字符串频繁拼接 | StringBuilder / join / list+join | 总量 O(n)，避免 O(n²) |
| 子串查找 | 标准库 find/index；多模式用 Aho-Corasick | 视库实现 |
| 带淘汰的缓存 | LRU（OrderedDict / 保序 Map） | O(1) |
| 大文件 / 大流 | 迭代器 / 流式 API，绝不整体读入 | 内存 O(chunk) |

## 2. 热路径清单（进入循环前的仪式）

- [ ] 循环不变量全部提到循环外（方法调用、属性访问、正则编译、常量表达式）。
- [ ] 容器预分配容量（size hint），避免反复扩容拷贝。
- [ ] 循环体内零分配为目标：复用缓冲、用视图/切片代替拷贝、避免装箱。
- [ ] 高频查找提前建索引（Set/Map），杜绝循环内线性扫描。
- [ ] 用局部变量缓存高频访问的属性/键。
- [ ] 短路：能提前 break/return 的分支放前面；条件按命中率排序。
- [ ] 数值计算：避免重复开方/除法（用乘法逆元）、查表代替重算。

## 3. I/O 模式（多数应用的真瓶颈）

- **批量**：N 次小请求合并成 1 次大请求（bulk insert、批量 API、pipeline）。N+1 查询是最常见的性能事故。
- **并发**：互不依赖的 I/O 并行发出（async/await、线程池、Promise.all）；有依赖才串行。
- **流式**：大文件/大响应分块处理，内存占用 O(chunk) 而不是 O(全量)。
- **缓存**：读多写少的数据加缓存层；**必须同时设计失效策略与容量上界**。
- **缓冲**：小块写合并后落盘（buffered writer / 事务批量提交）。
- **就近**：把计算搬到数据旁边（数据库端聚合、边缘节点），而不是把数据搬到计算旁边。
- **预取**：可预测的下一步数据提前加载。

## 4. 内存模式

- 分清**拷贝 vs 视图**：切片/引用/内存映射零拷贝；确需隔离才深拷贝。
- 深拷贝的替代品：不可变数据结构、写时复制（COW）、结构共享。
- 对象池只对"分配确实是瓶颈且对象生命周期清晰"的场景使用；现代 GC 下多数场景不值得。
- 泄漏三源头：未注销的监听/回调、无淘汰的缓存、意外持有大对象的闭包。
- 大集合处理：生成器/迭代器 > 物化列表；能 stream 就不 collect。
- 字符串在多数语言中不可变，循环 += 是 O(n²)，一律 join / builder。

## 5. 并发模式

- I/O 密集 → **并发**（async / 协程 / 少量线程）；CPU 密集 → **并行**（多进程 / worker / 多核线程）。
- 首选**不共享**：消息传递 / 任务分发 / 每线程独立累加后合并，优于加锁共享。
- 必须共享时：缩小临界区；读多写少用读写锁或不可变快照。
- 任务粒度要粗：单任务执行时间应远大于调度开销；海量微任务先分批。
- 永远假设并发代码会被真实并发执行：竞态在测试里藏得住，在生产里藏不住。

## 6. 常见性能反模式 → 处方

| 反模式 | 处方 |
|---|---|
| 循环内 `list.contains(x)` | 循环外建 Set，O(n²) → O(n) |
| 循环内编译正则 / 创建 formatter | 提到模块级或循环外，一次编译多次用 |
| N+1 查询（循环里逐条查库/请求） | 一次批量查询 + 内存 join |
| 排序后取最大/最小 | 用 max/min 或堆，O(n log n) → O(n) / O(log n) |
| `JSON.parse(JSON.stringify(x))` 式深拷贝 | 结构化拷贝 API / 重新设计为不可变 |
| 递归展开大输入（无记忆化） | 记忆化 / 改迭代 / 换 DP |
| 字符串循环 += | join / StringBuilder |
| 先物化全量再过滤 | 生成器链 / 流式 filter，惰性求值 |
| 用异常做正常控制流 | 返回 Result / 错误码，异常只留给异常 |
| 无失效策略的缓存 | 加 TTL / LRU / 明确失效事件 |
| 整个文件读成字符串再按行处理 | 按行迭代 / 流式读取 |
| 同步 I/O 卡在事件循环 / UI 线程 | 移入线程池或改异步 |

## 7. 测量方法（微观优化的前置条件）

1. 先问复杂度：输入翻倍，耗时翻倍（O(n)）还是翻四倍（O(n²)）？这是最快的量级检测。
2. 用 profiler 找热点（py-spy/cProfile、DevTools/clinic、perf/pprof、async-profiler、VTune），不凭直觉。
3. Benchmark 规则：预热、多次取中位数、隔离 GC 噪声、对比相对变化而非绝对毫秒。
4. 每次只改一个变量，改完重测；没有变快的"优化"回滚。
5. 把测量结果写进代码注释，例：`// 2026-10 profile: 此处占 40% CPU，改 Int32Array 后 3.2x`。

## 8. 语言速记

- **Python**：内置容器与推导式 > 手写循环；热路径考虑 numpy / 向量化 / 生成器；避免内循环里的属性链查找；GIL 下 CPU 密集用多进程或 C 扩展。
- **JS/TS**：Map/Set 优于普通对象做字典；TypedArray 处理大块数值；保持对象形状一致（隐藏类稳定）、避免 megamorphic 调用；`Array.join` 拼接；事件循环里不跑同步重活。
- **Go**：slice 预分配容量（`make([]T, 0, n)`）；sync.Pool 复用高频临时对象；小结构体值接收者、大结构体指针接收者；channel 编排、mutex 保护状态，二选一别混用。
- **Java/Kotlin**：集合给初始容量；基本类型优于装箱；Stream 在热路径谨慎（分配开销）；StringBuilder 拼接；小对象写法有利于逃逸分析。
- **C/C++/Rust**：数据布局决定性能。连续内存（数组/Vec）优于指针追逐；避免伪共享；移动语义/借用代替拷贝；热路径禁用动态分配（预分配、arena、SmallVec）。
- **SQL**：先看执行计划；WHERE/JOIN 列建索引；避免 SELECT *；大集合用 EXISTS 代替 IN；聚合下推到数据库做。
