# dsh-bettercode

English | [中文](README.zh-CN.md)

一个给 AI agent 的"写码纪律"skill：让模型像顶级工程师一样写代码 ——
设计期就定对复杂度、实现期逻辑干净清晰、性能靠测量而非直觉，
从源头杜绝屎山。

语言无关。写新代码、重构遗留代码、代码审查都适用。

## 为什么需要这个 skill

现在的 LLM 已经能写出**能跑**的代码。它们缺的往往是资深工程师的纪律：

- 写循环**之前**先选数据结构（"能跑"的代码里藏着 O(n²)）；
- 区分设计期性能（永远做对）和微观优化（先测量再做）；
- 拒绝在"临时方案"上再打一个补丁；
- 交付前过一遍自检清单，而不是把第一版草稿直接交出去。

`dsh-bettercode` 把这套纪律变成一条**带闸门的工作流** + 一组**可检查的硬规则**
（函数 ≤ 40 行、嵌套 ≤ 3 层、重复第 3 次必须抽象、零死代码、零魔法值……），
外加两份按需加载的参考手册。

## 工作原理

```
路由     先选模式                   写新代码 → Phase 1-5 · 重构遗留 → 重构纪律 + Phase 2-5
                                    · 审查 → 自检清单 + 坏味道目录
Phase 1  动手前（≤2 分钟）          契约 · 数据规模 N · 是否热路径 · 延迟还是吞吐
                                    → 复杂度预算（一次性脚本 vs N>10⁵ 热路径）
Phase 2  设计                       数据结构选择表 · 分层 · 纯核心 / I/O 边缘
Phase 3  编写                       硬规则：早返回、单一职责、DRY（第三次必抽象）、
                                    零死代码、零魔法值、禁止布尔陷阱、命令查询分离……
Phase 4  性能                       "永远做"清单（循环不变量外提、I/O 批量+并发、
                                    循环前建索引……）vs "先测量"的微观优化
                                    + 结构换常数成本的自觉权衡
Phase 5  交付前自检                  10 条清单，不过关就改，改完再过
─────────────────────────────────
重构模式                            先锁行为（特征测试）→ 怪癖保留标注 → 差分对拍证明等价
                                    → 兼容层显式化 → 交付报告；验证深度与变更风险成比例
红线                                7 个屎山信号 → 停下重构，不许继续堆
```

两份 reference **按需加载**（不到需要时不占上下文）：

| 文件 | 何时加载 |
|---|---|
| `references/performance-patterns.md` | 性能设计 / 优化 / 排查慢代码时 —— 数据结构选择表、热路径仪式、I/O·内存·并发模式、12 组反模式→处方、测量方法、各语言速记 |
| `references/code-smells.md` | 审查 / 重构 / 踩红线时 —— 20 类坏味道按"症状→病因→处方"组织，附重构安全守则 |

## 安装

### DeepSeek Harness (DSH)

把 `dsh-bettercode/` 目录复制进用户级 skill 根目录（自动发现，无需重启）：

```
~/.dsh/skills/dsh-bettercode/
```

或放到项目级：

```
<project>/.dsh/skills/dsh-bettercode/
```

### 其他 agent（Claude Code / Cursor / Codex CLI / Gemini CLI / opencode）

本 skill 就是一个纯 `SKILL.md` + `references/` 的 bundle。丢进你工具的
skill/rules 目录，或把 `SKILL.md` 贴进系统规则即可。

## 用法

- **自动**：description 覆盖了"编写 / 重构 / 审查 / 优化"等场景，
  兼容的 host 会自行加载。
- **手动**：说"用 dsh-bettercode 实现/重构 ……"。

## 效果验证（A/B）

用同模型的 A/B 对照（带 skill vs 不带）在三个任务上验证，
完整数据见 [EVALUATION.md](EVALUATION.md)：

- **重构遗留屎山**（137 行上帝函数、20 处埋雷、O(n²) 查找、裸 `except:`、
  布尔陷阱）：两组都通过 400 组随机差分对拍（行为可证明完全一致）。
  skill 组消除坏味道 ~19.5/20 vs 基线 ~17/20，主编排函数 47 行 vs 80 行，
  修复了基线放弃的布尔陷阱，并把保留的怪癖与复杂度论证写进模块 docstring。
- **同一文件的代码审查**（26 处埋雷）：skill 组召回 26/26 vs 基线 ~24/26，
  性能条目 9 vs 7，且使用统一术语体系而非临场措辞。
- **写新的性能敏感组件**（滑动窗口限流器）：两组都选出最优 deque 设计、
  AST 质量分都是 100/100 —— 规格清晰的新写任务上强基线模型本来就能做好；
  skill 的增量在于显式写出复杂度论证、明确拒绝无测量的微观优化。

诚实的结论：这个 skill 不是把差输出变好 —— 现代基线模型已能写出不错的代码。
它让**上限行为变成确定性事件**：每次都做到全覆盖审查、有纪律的重构、
写明取舍的工程表达。

## 这个 skill 自身的设计原则

- **可检查的规则 > 含糊的建议**。"≤ 40 行"可验证；"写干净点"不可验证。
- **常驻上下文最小化**。SKILL.md 刻意精简；手册只在对应 phase 才加载。
- **兼顾两种失败模式**。既治屎山，也治过早优化 —— 微观优化必须有
  profile 证据，并写进注释。
- **闸门，而非口号**。每个 phase 以一份必须通过才能交付的清单收尾。
